# LingoWave infrastructure direction

The first production deployment is intentionally queue-first and scale-to-zero:

```text
React/Vite web → CloudFront → API Gateway HTTP API → Lambda control plane → Aurora PostgreSQL Serverless v2 (ledger + jobs)
                       ├── S3 private objects (signed upload/download URLs)
                       └── SQS → active worker fleet (Fargate Spot CPU or ECS/EC2 GPU, desired count 0 when idle)
```

The worker image is split from the Lambda-compatible API image. In `deployment_mode = "serverless"`, the Lambda API uses the Aurora Serverless v2 RDS Data API and does not need a VPC attachment or NAT Gateway. Large uploads continue to use presigned S3 URLs. Queue depth drives the active Fargate Spot CPU worker autoscaling policy; GPU capacity remains an optional ECS/EC2 fleet with desired capacity zero when idle. ECS tasks mount `/var/lib/lingowave/model-cache` at `/home/lingowave/.cache`, so model downloads are reused across task replacements while a GPU host remains alive; scale-to-zero intentionally discards that host-local cache, and cold-start time must remain visible in benchmarks.

Staging and production use separate Terraform variable files and separate S3
state keys under `terraform/environments/`. Initialize one explicitly with
`terraform init -reconfigure -backend-config=environments/backend-<environment>.hcl`
and apply with the matching `-var-file`. The production backend key preserves
the existing live state location; staging uses `lingowave/staging/terraform.tfstate`.

Required production controls before enabling public traffic:

- PostgreSQL-backed credit ledger with reserve/finalize/release transactions.
- Use `deployment_mode = "serverless"` for the near-zero-idle path. It provisions Lambda, API Gateway HTTP API, and Aurora Serverless v2 with a five-minute minimum auto-pause alongside the retained legacy path during Phase A. Keep `serverless_frontend_cutover=false` until Aurora data migration and direct API Gateway validation pass; enable it only in a separate reviewed cutover apply. The Aurora-managed Secrets Manager credential is retained because the RDS Data API requires a secret ARN.
- Set `enable_aurora_serverless=true`, run `PYTHONPATH=. python scripts/verify_aurora_engine.py --region eu-north-1 --engine-version 16.8`, and set `lambda_api_image` to the immutable Lambda image digest. Run `scripts/migrate_serverless.py` after the first apply and after schema changes with `SERVERLESS_MIGRATION_FUNCTION=<name>-migration`.
- Before planning, run `AWS_PROFILE=<profile> PYTHONPATH=. python scripts/verify_serverless_artifacts.py --region eu-north-1 --lambda-api-image <api-repository>@<lambda-digest> [--cpu-worker-image <worker-repository>@<cpu-digest>] [--ssm-parameter /lingowave/production/google-client-id]`; it fails if a digest is missing or mutable/tag-only, or if a mapped SSM SecureString parameter does not exist.
- Existing production migration is guarded: phase A sets `retain_legacy_rds=true`, `retain_legacy_api=true`, and `serverless_frontend_cutover=false` with the current legacy image/secrets. The old PostgreSQL instance, ECS API, ALB, and CloudFront route remain available for rollback while the new Lambda/API Gateway/Aurora path is validated directly. Copy data with `scripts/migrate_postgres_to_aurora.py` from a temporary VPC-reachable task, validate the new API, then enable the cutover flag and set both retain flags to `false` only in later reviewed applies.
- If `deployment_mode="legacy"`, the existing ECS/Fargate API, ALB, and provisioned PostgreSQL path remains available for rollback.
- Set `create_network=true` to let Terraform create a small two-AZ VPC, public worker subnets, isolated database subnets, and least-privilege worker/database security groups. Leave it false only when the deployment supplies existing `vpc_id`, subnet IDs, and security-group IDs.
- Pass `ssm_parameter_map` plus explicit `ssm_parameter_arns` for Lambda configuration/secrets. Lambda reads SSM Standard values at cold start; no secret value belongs in Terraform variables, images, or git. Keep `worker_secrets` only for the legacy ECS worker path.
- Bootstrap those parameters from a controlled shell environment with `AWS_PROFILE=<profile> python scripts/bootstrap_ssm_parameters.py --region eu-north-1 --parameter GOOGLE_CLIENT_ID=/lingowave/production/google-client-id --parameter GOOGLE_CLIENT_SECRET=/lingowave/production/google-client-secret --overwrite`; the helper sends values directly to SSM SecureString and never prints them. Keep the Terraform `ssm_parameter_map` keys equal to the application environment names and allow the exact parameter ARNs through `ssm_parameter_arns`.
- The production default `translation_provider = "google-deep-translator"` uses `deep-translator`/`GoogleTranslator` for fast segment translation. When generated speech exceeds the configured timing tolerance, `translation_refinement_provider = "hymt2"` lazily runs `tencent/Hy-MT2-1.8B` once per segment to shorten the spoken text before bounded FFmpeg speed adjustment. `aws-translate` remains an optional primary/comparison mode (and Terraform grants `translate:TranslateText` only when selected); `configured-api` remains available for an external endpoint and key through `worker_secrets`.
- S3 object validation, lifecycle retention rules, and signed URLs.
- SQS visibility timeout, bounded retries, idempotency keys, and dead-letter queue.
- For SES mail, set `mail_provider = "ses"`, use a verified `mail_from`, and pass its `ses_identity_arn`; Terraform scopes `ses:SendEmail` to that identity.
- `sqs_visibility_timeout_seconds` defaults to 3600 seconds and should cover the measured worst-case dubbing job; it is configurable up to AWS's 12-hour maximum.
- CloudWatch metrics for queue age, successful minutes, startup time, and actual cost per minute.
- Separate model images for transcription/separation, voice, and optional lip sync.
- No permanent GPU service; Spot capacity is optional only after interruption recovery is proven.

The exact AWS service choice (ECS GPU capacity providers vs. managed EC2 queue workers vs. SageMaker async) should be selected from measured `$ / successfully processed minute`, not the lowest hourly instance price. This repository includes the domain/config layer to store those measurements without embedding guesses in application logic.

The Terraform implementation supports one active queue-backed fleet at a time through `worker_compute_mode`: `cpu` uses Fargate Spot, `gpu` uses the ECS EC2 GPU capacity provider, and `disabled` leaves both fleets idle. SQS CloudWatch step scaling starts workers from the visible backlog and adds capacity in larger steps as waiting jobs accumulate. In-flight messages are included only in the scale-in guard, so one long-running job does not continuously create idle workers. A sustained empty queue scales the active service back to zero; the GPU capacity provider then returns its ASG to zero as tasks drain. `gpu_market_type = "spot"` is available after an interruption-acceptance run; the production example stays on-demand until that evidence exists. AWS cautions against using raw `ApproximateNumberOfMessagesVisible` as a target-tracking metric because message count is not proportional to instance count, so these policies intentionally use bounded step scaling and a maximum worker count. CloudWatch metrics are minute-granularity, so the expected activation path is queue submission followed by worker launch within the AWS alarm/placement window, not a synchronous API call from the browser.

AWS Batch was evaluated for the worker fleet. The current ECS scale-to-zero path is intentional: the worker holds the SQS visibility lease while processing and deletes or requeues the message only after the database job reaches a settled state. An SQS-to-Batch EventBridge Pipe acknowledges the SQS message when `SubmitJob` succeeds, before the long-running container completes; adopting it safely would require a separate dispatcher plus Batch-job reconciliation/recovery service. That extra always-on control path would weaken the existing failure semantics and add complexity without reducing idle compute below the current zero-task/zero-instance design. The documented default therefore keeps ECS/Fargate Spot for CPU and ECS/EC2 GPU capacity as the reliable, technically appropriate scale-to-zero implementation; Batch remains a future option after an end-to-end job-level acknowledgement/reconciliation proof.

The legacy path sets `api_image` to the published Uvicorn API image and runs it behind an HTTPS ALB. Phase A also sets `lambda_api_image` to the Lambda image while retaining that ALB until `serverless_frontend_cutover` is explicitly enabled; the later cleanup apply can remove the legacy path. The Lambda image includes only API/runtime dependencies and FFmpeg for lightweight media inspection; AI model weights remain worker-side and are fetched/cached at job time.

For a first launch without a custom domain, set `frontend_enabled=true` and leave `api_certificate_arn` empty. Terraform then creates one private S3 frontend bucket and a CloudFront distribution with the default AWS HTTPS certificate; `/api/*`, `/v1/*`, and `/health` route to API Gateway in serverless mode, or to the ALB in legacy mode. Build the frontend with `VITE_API_URL=''`, pass the absolute `frontend_dist_dir`, and set `frontend_origin` to the resulting `frontend_url` on the upload apply. The `api_url` and `frontend_url` outputs are the same CloudFront URL. Add a custom ACM certificate later when a domain is available.

After apply, use the Terraform outputs for `api_url`, `S3_BUCKET`, `SQS_QUEUE_URL`, `AWS_REGION`, and the generated network IDs. In serverless mode there is no continuously running API task: Lambda is invoked per request, Aurora compute pauses after idle, and the selected CPU or GPU worker service scales from zero on demand and returns to zero after the SQS queue, including in-flight work, has drained. The production example sets `cost_alert_email` and a `$5` monthly baseline budget so AWS Budget and Cost Anomaly Detection notifications are created after the placeholder is replaced with a real recipient; leave it empty only for an explicitly intentional no-email environment.

The checked-in `.github/workflows/aws-serverless-cpu-scale-to-zero.yml` is the post-cutover acceptance gate. It starts only from a verified zero worker baseline, submits the real API/S3/SQS/media path, proves ECS queue-driven scale-out, captures evidence, and restores the prior task definition and zero baseline even when the test fails.

Keep `cpu_worker_max_count=1` for the current `4096 CPU / 16384 MiB` worker shape unless the account’s Fargate vCPU quota has been raised and a measured workload warrants additional concurrency; `worker_max_count` remains the separate GPU fleet limit.

The GitHub OIDC image-publish role is restricted to `github_actions_branch` (default `codex/production-saas`); pull requests and other branches do not receive production ECR credentials. Keep that branch restriction aligned with the publish workflow before enabling it.

## Cost baseline and guardrails

The supplied `costs.csv` contains three billable days totaling `$9.8579798828`, which is a simple 30-day run-rate of about `$98.58`; it is not a full-month forecast. ECS, ECR, ALB, RDS, and VPC represent 99.39% of that sample. Removing the always-on API/ALB/RDS path and idle GPU network footprint removes `$8.2224355072` from the three-day sample, or about `$82.22` from its run-rate, before accounting for the new serverless baseline.

The target of approximately `$5/month` is an idle-baseline target excluding durable media storage, domain registration, taxes, and user-driven worker compute. It depends on ECR storage after the lifecycle policy, CloudWatch log volume, Aurora storage/backups, and account-specific free-tier eligibility. Lambda, API Gateway, SQS, and Aurora capacity are usage-based; Fargate Spot and GPU workers remain variable processing costs. Tag any image that must survive routine cleanup with an explicit `release-` prefix, review the ECR lifecycle preview before the first apply, and re-check Cost Explorer after one complete idle month before treating the target as a guarantee.
